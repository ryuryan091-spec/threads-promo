# P76 오류 증거 수집·재시도 제어 상세설계 (2026-11-02)
관련 장애: #18, 실행 41429749313. 기존 운영 커밋: 3b9ffaa.

## 문제와 변경
기존 진단에서 unknown은 메시지 누락과 미분류를 구분하지 못했다. retryable=false도 다음 예약 실행의 재시도에 연결되지 않았다.
- 공개 진단: message_present, message_length, 허용목록 detail_code 추가. 조직/워크스페이스 지출 한도 공식 문구 분류.
- error.details.error_code=enforced_spend_limit_reached는 429여도 보류한다.
- 408/409/일반429/5xx와 SDK 연결·타임아웃 예외는 총3회 안에서 다음 실행 재시도. 나머지 API 실패는 결과코드에 :hold를 붙인다.
- hold 결과는 다음 실행의 _retryable에서 제외한다. 보류만 남아 생성할 작업이 없을 때 Actions도 failed로 표시한다. 반복 T5나 LLM 호출은 하지 않는다.
- 최초 실패 T5에는 원인 힌트와 request_id, 보류 안내 및 기존 원장 링크를 포함한다.
- 비공개 DB-12 해당 원고 페이지의 'API 오류 진단 (JSON)' 절에 안전한 진단과 마스킹된 메시지, 시각, 시도 횟수를 저장한다. 로그/Telegram/PR에는 메시지를 싣지 않는다.

## 비공개 메시지 처리
SDK 예외 전체나 request를 문자열화하지 않고 body.error.message(또는 평탄한 body.message)만 사용한다.
입력 system/messages의 전체 텍스트와 줄별 일치값, 큰따옴표/백틱 인용문을 제거한다. 기존 redact로 등록 자격증명/식별자/토큰 패턴을 마스킹한 후 공백 정규화, 1200자로 제한한다.
부분적으로 재서술된 비인용 입력은 남을 수 있으므로 결과를 공개용으로 간주하지 않는다. 기존 비공개 원장에만 저장하며 해당 페이지 공개 공유는 금지한다.
메시지 누락은 빈 문자열로 저장하고 존재 여부/길이로 구분한다. 기존 실행에서 버린 원문은 복원할 수 없다.
원장 저장 실패 시 이미 기록한 hold를 유지하고 diagnostic:persist_failed로 실행 실패를 남긴다. 저장 예외 원문은 출력하지 않는다.

## 재개 및 기존 데이터
기존 api:BadRequestError:400에는 hold가 없으므로 남은 총3회 범위 내에서 다음 실행에 증거 수집이 가능하다. 이미 3회 소진한 행은 자동 초기화하지 않는다.
새 hold는 코드 배포만으로 자동 해제하지 않는다. 원인 수정 후 운영자가 해당 행 결과코드를 감사 메모가 포함된 manual_resume 값으로 변경하고, 시도<3인지 확인해야 한다. 3회 소진 시 별도 명시적 초기화가 필요하다.
자동 원장 비용 초기화, Opus 전환, API 실패 원고 발행은 수행하지 않는다. 품질 경고의 기존 발행 정책은 유지한다.
