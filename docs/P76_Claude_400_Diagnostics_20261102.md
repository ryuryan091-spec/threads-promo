# P76 Claude HTTP 400 진단 상세설계 및 개발 결과

## 문제와 확인 근거
- 대상: run 41411731593, 기준 커밋 20fefed264e9ad9507c8d2a6adcc23b7485d8255.
- shadow에서 N1-BIBLE:write가 BadRequestError 400으로 실패했다.
- 이전 41326032002 / 41330181755 / 41336598363 실행은 실제 생성 응답을 받았다.
- 기존 코드는 서버 메시지를 버려 거절된 요청 항목을 확정할 수 없다. 키 또는 모델 오류로 단정하지 않는다.

## 변경 범위
1. novel_diagnostics.diagnose(error, params): 외부 호출 없는 순수 함수.
2. novel_llm.call의 공통 예외 처리에서 진단 JSON을 한 줄 기록.
3. 기존 LLMError 코드, 상태 전이, 종료코드, 재시도 횟수 및 API 요청은 유지.
4. main 병합과 shadow 재실행은 이번 개발 단계에 포함하지 않는다.

## 진단 계약
| 필드 | 처리 |
|---|---|
| http_status | 정수 100~599만 수용, 나머지 null |
| error_type | 고정된 API 오류 유형 허용목록, 나머지 unknown |
| field_hints | 서버 메시지 안의 고정 필드명만 추출; 원인 확정값이 아닌 단서 |
| request_id | req_ 뒤 영숫자 8~80자만 허용, 나머지 unavailable |
| config_sha256 | 모델·토큰 한도·thinking·output_config·betas·fallbacks를 정렬 직렬화 후 SHA256 앞 16자 |
| retryable | 408/409/429/5xx 여부; 진단용이며 재시도 동작을 변경하지 않음 |

프롬프트, 원고, 사용자 메시지, API 키, 헤더, 오류 본문은 출력하지 않는다.
오류 본문은 메모리에서 필드명 추출에만 이용한다. 해시는 요청 본문 전체가 아니라 요청 구성 비교용이다.
동일 오류의 stream/create 경로 모두 동일하게 진단한다. 메시지가 없거나 비정상 구조면 unknown/빈 목록으로 남긴다.

## 운영 확인 절차
1. 검토 후 변경을 main에 반영한다.
2. DB-12 N1-BIBLE 상태·시도 횟수·중단 여부를 확인한다. 3회 상한으로 제외된 경우 별도 복구 판단 없이 자동 초기화하지 않는다.
3. shadow 1회에서 diagnostic 로그를 확인한다. shadow는 실제 비용·노션 쓰기·텔레그램 전송을 수반한다.
4. http_status, error_type, field_hints, request_id로 요청 오류를 좁힌다. 힌트가 비어 있으면 원인은 미확정이다.
5. 식별한 원인만 수정하고 shadow에서 실제 생성 및 검수를 검증한다.

## 후속 개선 분리
- 핵심 API 실패를 Actions 실패로 표시하는 정책.
- API 요청 오류와 원고 검수 실패의 재시도 카운터 분리.
위 두 항목은 진단 수정과 별개로 상태 전이 및 복구 정책을 검토해야 한다.

## 테스트 결과
- 신규 진단 테스트 10건 및 기존 소설 테스트 포함 112건 통과.
- 400/401/403/429/500, 메시지 내 비밀문구, 비정상 오류 구조, request ID 개행 주입, 구성 해시, stream/create 경로 검증.
- p76 전체 테스트는 PyYAML 미설치로 수집 중단; 전체 통과로 보고하지 않는다.
- 외부 API 실제 호출 및 운영 재실행 없음. 400의 서버 상세 원인은 아직 미확정.

## 롤백
novel_llm.py의 진단 호출과 import를 되돌리고 신규 진단 모듈을 제거하면 기존 오류 처리로 복귀한다. DB 스키마 및 Secret 변경 없음.
