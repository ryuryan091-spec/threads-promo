- 운영 정본 NB-S 스키마와 요청 설정으로 계산한 지문이 실패 로그와 일치한다. 정본 arc가 배열에서 e1..e7 필수 객체로 변경되었다.
- 스키마 복잡성/컴파일 문제는 조사 대상이다. 지문 일치는 요청 식별 증거이며 오류 원인 증거가 아니다.
- 확정 결함: 기존 진단은 고정 필드명만 찾아 field_hints에 기록한다. 'Schema is too complex for compilation.' 같은 오류와 크레딧 오류는 구분되지 않는다.
- mock 테스트 통과는 실제 Anthropic의 운영 스키마 수락을 증명하지 않는다.

## 상세설계
### 1. 안전한 오류 분류 — 이번 수정
대상: p76/novel_diagnostics.py.
기존 필드/설정 지문/request_id를 유지하고 reason_hint를 추가한다.
HTTP 400 + invalid_request_error에서만 알려진 문구를 판별한다.

| reason_hint | 의미 / 후속 조치 |
| --- | --- |
| schema_compilation_complexity | 스키마 컴파일 복잡성 메시지와 일치. 동일 스키마 최소 요청 재현 후 단순화 검증 |
| schema_compilation_timeout | 컴파일 시간 초과 메시지와 일치. 공급자 request_id 추적 및 최소 요청 비교 |
| credit_balance | 크레딧 관련 메시지와 일치. 실제 Actions 키의 조직/워크스페이스와 Console 대조 |
| ambiguous | 서로 다른 원인 문구가 동시에 나타남. 원인 확정 금지 |
| unknown | 알려진 문구 없음. request_id로 공급자 확인, 분류 규칙 보완 |

reason_hint는 메시지 기반 힌트이며 확정 원인이나 자동 재시도 정책이 아니다. 키, 프롬프트, 출력 원고, 공급자 메시지 원문은 로그에 남기지 않는다. 필드명 탐지는 대소문자를 구분하지 않는다. 기존 retryable 계산과 총 3회 제한을 유지한다.

### 2. 원인 확정 절차 — 후속 운영 검증
1. 진단 변경 반영 후 다음 통제된 shadow 실행에서 reason_hint/request_id/설정 지문을 확보한다. 무제한 재실행이나 비용/시도 자동 초기화는 금지한다.
2. 스키마 원인 힌트이면 동일 Sonnet 모델과 운영 NB-S 스키마를 사용하되, 짧은 비민감 입력으로 계약 검증한다. 별도 검증 경로는 Threads 발행/Notion 원고 변경 없이 실행한다. 실제 호출 비용과 호출 수를 기록한다.
3. 원본 스키마를 기준군으로 보존하고 한 번에 한 요소만 바꿔 비교한다. 반복 episode 정의의 $defs/$ref 공유 또는 요청 분리는 후보이며, 더 작은 JSON이 반드시 더 쉬운 컴파일을 뜻하지 않는다.
4. 개선 스키마가 수락되더라도 e1..e7 완전성, normalize_arc 이후 순서/회차, bible 검증, 수정 요청 병합이 유지되는지 확인한다. 비공개 프롬프트 정본을 공개 저장소에 복사하지 않는다.
5. credit_balance이면 키 원문 노출 없이 소속 조직을 대조한다. unknown이면 request_id와 비민감 설정으로 공급자에 확인한다. 임의로 스키마를 바꾸거나 크레딧 부족으로 보고하지 않는다.
